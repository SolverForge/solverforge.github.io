**solverforge-cli 3.9.0 was published on November 9, 2026**, following
`3.8.3`, which scaffolds `solverforge 0.24.0`. The 3.9.x packages target
`solverforge 0.25.0`; the web shell keeps `solverforge-ui 0.9.1` and
`solverforge-maps 2.3.3`, and the MCP shell keeps `rmcp 3.9.0`. Existing
applications keep their own manifests and generated source.

## What Changed

### Fresh scaffolds target SolverForge 0.25.0

New projects pin `solverforge 0.25.0`. The generated `solver.toml` still
declares only `seconds_spent_limit = 30`, which means the same thing on 0.25.0:
the solve stops after 30 seconds, and no other limit is added.

### Disabled snapshot analysis has a response

`SolverManager::analyze_snapshot` returns
`SolverManagerError::SnapshotAnalysisDisabled` for a job that ran with
`score_director.constraint_match_enabled = false`. The web and API shells
answer `/jobs/{id}/analysis` for such a job with `409 Conflict`, and the MCP
shell reports it as invalid params. The generated `solver.toml` declares no
`[score_director]` table, so analysis stays enabled.

### `move_thread_count` validation and comments follow the runtime

`solverforge check` and `solverforge config set` accept `move_thread_count` as
`"auto"`, `"none"`, or `{ count = N }` with `N` of at least 1; `{ count = 0 }`
is rejected, as the runtime rejects it. The commented block in the generated
`solver.toml` describes the runtime default: `"auto"` uses up to four
evaluators and runs each step sequentially or in parallel windows, whichever
its measurements say is faster, while `"none"` stays sequential.

## Upgrade Checklist

- Install with `cargo install solverforge-cli --version 3.9.0 --locked --force`
  and inspect `solverforge --version`.
- Upgrading the CLI does not change existing apps. To move an app to
  `solverforge 0.25.0`, follow the core release note's checklist; an app
  generated by 3.8.x also needs the `SnapshotAnalysisDisabled` arm in its
  `/jobs/{id}/analysis` error mapping, because the runtime error enum is
  matched exhaustively.
- Replace `move_thread_count = { count = 0 }` with `"none"` or a positive
  count; `solverforge check` reports it.
