**solverforge 0.19.9** is published on crates.io and released on GitHub
(2026-10-08), following `solverforge 0.19.8`. At publication, `cargo add solverforge` installed
0.19.9 and docs.rs served the 0.19.9 API. The Rust `1.95` floor, planning
model, and compiled search-runtime graph remain unchanged. This release moves
relational scoring onto a common typed operator tree and fixes a managed-job
pause/resume race.

## What Changed

### Each join can use its own relationship

A chained join no longer requires all sources to share one key domain. The
first join can match a numeric shift ID through `equal_bi(...)`; the next can
match an employee code through `equal_on(left_row_key, right_row_key)`. The
left key sees the complete prior borrowed row, so it can use any earlier
binding, not just the most recently introduced source. Independent joins can
use different key types.

`equal_on(...)` operates on row views: a binary prior row is a
`Pair<Leaf<A>, Leaf<B>>`, with entities available through `.left.entity` and
`.right.entity`. Use named function items with explicit borrow lifetimes for
nested-row keys. An annotated closure can fix a lifetime too narrowly for the
higher-ranked execution bound. Replace the historical third-source
`.join((source, key))` form with `.join((source, condition))`; each chained
relationship now compiles its own condition rather than extending a shared key.

Comparison, interval-overlap, and composed conditions also compile into concrete
plans. Equality uses hash indexes; comparison and overlap use their ordered or
interval candidate strategies; arbitrary predicates use an explicit scan.
Multiple equality components form a heterogeneous composite key, with other
conditions retained as residual predicates.

### Fluent joins continue past Penta

Named cross `Bi`, `Tri`, `Quad`, and `Penta` streams are ergonomic adapters over
the same tree. `Penta::join(...)` returns `stream::chain::Chain`, whose
`.join(...)` can keep nesting `JoinNode`s without a fixed binding-count ceiling.
`Chain::filter(...)` preserves row identities, and `penalize(...)` or
`reward(...)` followed by `.named(...)` finalizes the chain through
`OperatorTerminal`. Past the named arities, keys and weights receive recursive
borrowed rows rather than another fixed-arity argument list.

### Groups can be join inputs

A unary grouped stream can continue with
`.group_by(key, collector).join((collection, target_key))`, scoring the group
key, aggregate, and matching target together. A group result is an upstream row,
not necessarily a finalized score. At the low level either join input can be a
`GroupNode`, including groups of previously joined rows.

Contributor changes replace surviving aggregate rows during both retraction and
insertion. `RowChanges { removed, inserted }` carries those replacements;
consumers remove old indexes and contributions before inserting the new rows.
Collector results stay accumulator-owned, including non-Clone payloads, and
explanations retain all contributing source bindings.

### One final operator-tree architecture

The final tag uses `JoinNode` with compiled conditions and
`constraint::relational::OperatorTerminal`, not the intermediate `EquiJoin`
terminal introduced early in this development range. The former
`CrossJoinEngine`, cross-bi/cross-tri incremental modules, per-arity self-join
engines, flattened-bi engine, and standalone existence engine were removed.
Same-collection unique combinations use `SelfJoinNode`; cross joins, existence,
flattened joins, and complemented grouping route through the operator protocol.
Specialized unary, balance, grouped-sharing, and projected families still exist;
this is not a claim that every fluent family has become one generic adapter.

The module-level low-level surface in
`solverforge_scoring::stream::relational::operator` exposes `CollectionNode`,
`FilterNode`, `MergeNode`, `ProjectNode`, `GroupNode`, `ExistenceNode`,
`FlattenNode`, `ComplementNode`, `JoinNode`, and `SelfJoinNode`. These are
concrete generic row producers, not facade-root exports or a promise that every
producer has a uniform fluent method:

- filters preserve accepted identities on either join input;
- bag unions preserve branch identities and duplicate-valued emissions;
- projections own fresh zero-or-more values without requiring payload clones;
- semi/anti joins publish left membership only and retain match counts;
- flattening borrows child slices while keeping parent provenance;
- target-domain complements publish real matches or owned defaults, preserving
  duplicate target identities.

Full evaluation owns freshly derived values separately from retained incremental
state. Borrowed views do not keep solution references across notifications;
generational handles identify rows, while semantic source indexes and full
provenance remain available for filters and explanations.

### Sharing has a specific boundary

The existing `#[solverforge_constraints]` compiler can still share supported
same-binding and syntax-proved identical grouped terminal chains, including
projected, cross-grouped, and complemented-grouped families. Cross-grouped
matching now uses the common join operator inside that retained sharing path.
This does **not** add arbitrary compiler-owned sharing of a derived operator
tree across multiple consumers. A reusable projection, group, or join alone
is not a declaration of shared execution.

### Resume cannot lose the worker wakeup

A resume or cancellation could clear the pause request and notify between a
worker's predicate check and its condition-variable wait. The worker then
missed the notification and stayed blocked. Both paths now clear the request
and wake the worker while holding the same pause gate used by the wait. The
worker either sees the cleared request before waiting or is already waiting
and receives the wakeup. Structural-completion and snapshot boundaries are
unchanged.

## Upgrade Checklist

- Update direct Rust dependencies and confirm `Cargo.lock` resolves `0.19.9`.
- Replace imports of removed low-level engines with the supported fluent surface
  or the module-scoped operator protocol; the 0.19.8 engine description is history.
- Use `equal_on(...)` when a later join needs its own relationship or key type;
  preserve explicit lifetimes on nested-row function items.
- Re-run incremental/full-score parity, source-localization, aggregate replacement,
  explanation, and managed pause/resume tests for your application.
- Upgrade CLI-generated apps deliberately. CLI 3.3.3 still scaffolds core 0.19.7;
  publishing 0.19.9 does not retarget a scaffold or rebuild a Python wheel.
