**solverforge 0.19.8** is published on crates.io and released on GitHub
(2026-10-02), so `cargo add solverforge` installs 0.19.8 and docs.rs serves the
0.19.8 API. The previous package, `solverforge 0.19.7`, put every workspace
version surface under the release tooling. This release keeps the Rust `1.95`
toolchain floor and the compiled runtime-graph execution model unchanged, and
moves the scoring surface, not the runtime contract.

## What Changed

### Keyed cross joins reach a third source

Cross-bi streams dead-ended at arity 2. Their surface had `filter`,
`flatten_last`, `group_by`, `project`, and weighting, but no way to introduce a
third source, so a rule over three keyed sources had to denormalize a joined
pair into a synthetic row type first — or fall back to a hand-written
constraint.

The bi stream now carries an inherent `.join((extractor_c, key_c))` that
extends the joined `(A, B)` pairs with a third source `C`:

```rust
type Streams = ConstraintFactory<Schedule, SoftScore>;

Streams::new()
    .for_each(Schedule::shifts())
    .join((
        Streams::new().for_each(Schedule::employees()),
        equal_bi(
            |shift: &Shift| shift.employee_idx,
            |employee: &Employee| Some(employee.index),
        ),
    ))
    .join((Schedule::unavailability(), |u: &Unavailability| u.employee_idx))
    .penalize(|_shift: &Shift, _employee: &Employee, _u: &Unavailability| SoftScore::of(1))
    .named("Shift falls on an unavailability day")
```

The bi stream's own keys stay authoritative for `A` and `B`, and the join target
carries only the new source and its key, so the engine keeps probing one shared
key domain. The retained bi filter is lifted into the tri chain rather than
dropped, which is what preserves the filter contract and the semantic source
indexes across the arity change.

Three-source joins are also reachable through `#[solverforge_constraints]`.
Raw join chains flow through the attribute in passthrough mode and need no
compiler change; a compile-pass fixture now builds a
`uni -> cross bi -> cross tri -> penalize` chain through the macro and asserts
its score instead of only asserting that it compiles.

### One arity-generic engine behind cross-bi and cross-tri

The retained cross-bi constraint kept its match rows, per-source key indexes,
and `swap_remove` bucket maintenance as hand-written fields. Generalizing to
higher arities by hand-copying that bookkeeping per arity is where drift bugs
live, so the state moved into a single `CrossJoinEngine<N, K, Sc>` under a
hidden `constraint::cross_incremental` module: match rows keyed by
`[usize; N]` tuples, per-source key indexes, and per-source inverted row
buckets, all parameterized by source count.

`cross_bi_incremental::Bi` is now that engine at `N = 2`, and the new
`cross_tri_incremental::Tri` is the same engine at `N = 3`. The bi constraint's
public API, match semantics, and change localization are unchanged;
interleaved performance counters show roughly a 0.3% instruction delta, inside
the project's 5% hot-path gate.

### Cross-tri rows localize symmetric in any source

A retained `(A, B, C)` row requires `key_a(a) == key_b(b) == key_c(c)` plus the
tri filter. A change to any of the three sources probes that source's retained
key index and its candidate set, so incremental cost does not depend on which
source mutated. Filters receive semantic per-source slice indexes
(`a_idx, b_idx, c_idx`), matching the joined-filter-index contract the lower
arity joins already document, and change localization follows the same
`assert_localizes` contract — including failing explicitly on unlocalizable
callbacks rather than silently recomputing.

### The build gate runs the Rust checks CI runs

`make ci-local` previously ran a narrower set of Cargo commands than the
checked-in CI workflow: an all-feature workspace build and Clippy, but not the
all-target Clippy pass, the integration tests, or the doctests. A local run
could therefore pass while the same commit failed in CI. The Makefile now runs
the same validation commands as the workflow, keeping the change entirely in the
existing Makefile with no new scripts or dependencies.

## Upgrade Checklist

- Run `cargo update -p solverforge` and confirm the resolved version is `0.19.8`.
- Replace any three-source rule that denormalized a joined pair into a synthetic
  row type with a chained
  `.join((a, equal_bi(...))).join((c, key_c))` and score the `(A, B, C)` tuple
  directly.
- Two-source cross joins need no change; their surface, semantics, and change
  localization are unchanged, and the underlying engine was only reparented.
- Generated CLI projects still scaffold `solverforge 0.19.7`; move an app to
  0.19.8 deliberately and re-run its model, constraint, and solve tests, since
  the scaffold target and the current core release move independently.
