**solverforge-cli 3.8.2 was published on November 3, 2026**, following `3.8.1`
and `3.8.0` the same day; `3.8.0` introduced this line after `3.7.1` scaffolded
`solverforge 0.23.0`. The 3.8.x packages target `solverforge 0.24.0` and
`solverforge-ui 0.9.0` for the web UI; `3.8.2` moves the web shell's maps target
to `solverforge-maps 2.1.5`, and the MCP target stays `rmcp 3.8.0`. Existing applications keep their own
manifests and generated source.

## What Changed

### Fresh scaffolds target SolverForge 0.24.0 and solve

New projects pin `solverforge 0.24.0` and read `solver.toml` through
`solver_toml = "../../solver.toml"` on the planning solution, because the
runtime no longer reads it from the working directory. The generated
`solver.toml` declares only a 30-second termination limit and leaves the
phases to the runtime's model-aware default pipeline, with an explicit
pipeline shown in comments. A fresh project with no planning variables solves
to `COMPLETED`; the previous explicit local-search phase failed every solve on
0.24.0. Score analysis DTOs carry the runtime's `weightMultiplier`.

### Generators write code that compiles

- `--field` types are imported: std collections, the `chrono` types the CLI
  recognizes, and `use super::<Type>` for other names. The first `chrono`
  field adds `chrono` to `Cargo.toml`, and demo data seeds `Weekday` and `Utc`
  fields without `Default`.
- A `--field` type that is not defined in `src/domain/` prints a warning that
  names the type and where to define it.
- `--field id:...` and, for facts, `--field name:...` are rejected, because the
  generator already writes those fields.
- `generate score` refuses `BendableScore`: a planning solution's score must be
  parseable, and SolverForge 0.24.0 parses only `HardSoftScore`,
  `HardSoftDecimalScore`, `HardMediumSoftScore`, and `SoftScore`. A generic
  score type is imported by its bare name.
- `--unary --soft` penalizes instead of rewarding, `--unary` and `--reward`
  filter before scoring, and `--pair` counts each unordered pair once.
- `generate scalar-group` with an assignment target no longer leaves a
  construction phase that the runtime rejects.

Generated constraint skeletons and hook stubs still panic until their
placeholders are replaced; a solve before that ends `FAILED` with a message
naming the function and file.

### Formatting and the managed blocks agree

`solverforge new` emits rustfmt-clean sources, and every generator and
destroyer runs rustfmt on the Rust files it writes. `cargo fmt` no longer
breaks the CLI: managed `mod` lists are matched by name in rustfmt's sorted
order, and the rustfmt pass never moves a managed block marker. The CLI shell
compiles without dead-code warnings.

### Commands report what they do

- `solverforge check` states that it validates structure and did not compile
  the project.
- `solverforge server` honours the `PORT` environment variable after `--port`
  and before `.solverforgerc`.
- `solverforge routes` lists chained methods such as `get(a).delete(b)` and
  route calls split across lines.
- `solverforge test -- --nocapture` passes arguments after `--` to the test
  binaries.

### Destroy refuses dangling references

`destroy entity` and `destroy fact` refuse a type that constraint files or
planning variables still reference, list the referencing files, and change
nothing; the hint names the `destroy` commands to run first. In 3.8.1 the
file list uses forward slashes on every platform.

3.8.1 also re-renders `src/data/data_seed.rs` from other `generate` and
`destroy` commands only while the file still starts with the
`// @generated by solverforge-cli: data v1` header, so hand-written demo data
survives later commands. `generate data` still rewrites it on request.

### Web scaffolds identify themselves to Overpass

Web scaffolds from `3.8.2` pin `solverforge-maps 2.1.5`, which sends
`User-Agent: solverforge-maps/<version> (+<repository>)` to the Overpass API
instead of the fixed `SolverForge/0.5.0`; the public Overpass usage policy
requires a User-Agent that identifies the client. Projects scaffolded earlier
pick it up with `cargo update -p solverforge-maps --precise 2.1.5`.

## Upgrade Checklist

- Install with `cargo install solverforge-cli --version 3.8.2 --locked --force`
  and inspect `solverforge --version`.
- Upgrading the CLI does not change existing apps. To move an app to
  `solverforge 0.24.0`, follow the core release note's checklist; in
  particular add `solver_toml = "../../solver.toml"` to the planning solution
  and remove unknown `solver.toml` keys.
- Stop passing `--field id:...` or `--field name:...`; remove the header line
  from `src/data/data_seed.rs` once you own the demo data.
- Replace every generated placeholder before you solve, then run
  `cargo build`: `solverforge check` does not compile.
