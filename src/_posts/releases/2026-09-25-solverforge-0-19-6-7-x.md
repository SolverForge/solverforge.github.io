## What Changed

### Pinned entities are enforced, not just declared

`0.19.6` connects generated entity pin state to the existing
descriptor/extractor boundary, so solver phases can inspect the current entity
without reflecting on a field name. Manually assembled descriptors can supply
the same predicate, and unpinned descriptors keep the cheap unrestricted path.

Enforcement now covers the paths where a pinned decision could previously be
edited anyway:

- scalar edits to pinned entities are rejected
- pinned list owners keep their contents and order across construction and
  search
- pinned assignments are retained in exhaustive search
- sequential composite pin dispatch is covered by its own test
- pin scanning is skipped entirely for models without pins

Add `#[planning_pin]` to a boolean planning-entity field to preserve that
entity's input planning variables during solving. A pinned route owner keeps its
list contents and order; a pinned scalar keeps its input value. Pinned required
assignments that start unassigned cannot be completed and cause the solve to
fail; an optional pinned scalar may remain unassigned.

```rust
#[planning_entity]
pub struct Route {
    #[planning_id]
    pub id: usize,

    #[planning_pin]
    pub fixed: bool,

    #[planning_list_variable(element_collection = "visits")]
    pub visit_order: Vec<usize>,
}
```

The `pinned scheduling lifecycle` example verifies the contract end to end, so
a pinned plan survives every phase rather than only the first one that touches
the entity.

### One workspace version surface

`0.19.7` puts every workspace version surface under
`commit-and-tag-version`, so the workspace, the published crates, and the tags
are cut from a single declaration. The release tooling owns those surfaces
instead of relying on each crate to be updated by hand, which removes the class
of drift where a workspace member ships with a version no tag describes.

## Upgrade Checklist

- Run `cargo update -p solverforge` and confirm the resolved version is `0.19.8`
  before relying on pin enforcement, since the predicate only exists from
  `0.19.6`.
- If a model declares `#[planning_pin]`, re-run its model and lifecycle tests:
  a pinned required assignment that starts unassigned now fails the solve rather
  than being completed by construction.
- Models without pins need no change; pin scanning is skipped for them.
